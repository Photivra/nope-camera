## `ContentCredentialsManifest`

```swift
struct ContentCredentialsManifest
```

The manifest nope. writes for one file, as the JSON manifest definition the C2PA library takes.

It says only what nope. knows to be true (AGENTS.md, "Honesty"; issue #1, "Signing"):
- one `c2pa.created` action, with the IPTC digital source type `digitalCapture` (the image
  was captured from real life by a digital camera) and a plain description of what happened
  to the file;
- who generated the claim: ``ClaimGenerator`` (Photivra Nope Camera and its version).

Privacy rule: no time (`when`), creator, location, device, title, thumbnail or ingredient is
written, and the instance ID is a random UUID made for this file alone
(docs/PRIVACY.md, "Content Credentials").

## `ContentCredentialsSigner`

public, declared in `Sources/NopeSigning/ContentCredentialsSigner.swift`

```swift
struct ContentCredentialsSigner
```

Signs each file with C2PA Content Credentials, using a new key for every file, fully offline.

For each call to ``sign(_:)``:
1. the key provider creates a new P-256 key (the Secure Enclave on a device);
2. the key signs an anonymous, self-issued certificate for itself (``SelfIssuedCertificate``);
3. the C2PA library embeds a manifest (``ContentCredentialsManifest``) and the key signs the
   claim (ES256), with no timestamp authority and no network (``OfflineC2PAContext``);
4. the key is released and never used again.

Privacy rule: nothing in the signature identifies the person or the device, and no two files
share a key, certificate or instance ID (docs/PRIVACY.md, "Content Credentials"). The
certificate isn't chained to a trusted certificate authority, so validators show the signer
as untrusted; the signature proves the file is unchanged, not who took it.

Threading: the work is synchronous and CPU-bound (it hashes the whole file); call it off the
main actor. The type holds no mutable state, so one signer can serve concurrent calls.

## `ContentCredentialsSigner/embedInDNG(_:manifest:signer:)`

internal, declared in `Sources/NopeSigning/ContentCredentialsSigner.swift`

```swift
static func embedInDNG(_ data: Data, manifest: ContentCredentialsManifest, signer: sending Signer) throws -> Data
```

Signs a DNG with the C2PA data-hash workflow, keeping IFD0 in place.

1. The library makes a placeholder store of the final size.
2. ``DNGManifestSlot`` inserts tag 52545 into IFD0 and puts the placeholder at the end.
3. The library hashes the file with the store excluded (`c2pa.hash.data`, C2PA 2.2,
   section 9.2) and signs the claim.
4. The signed store, the same size as the placeholder, replaces it, so the hash still holds.

- Parameters:
  - data: The DNG.
  - manifest: The manifest to embed.
  - signer: The file's one-use signer; the context takes it.
- Returns: The signed DNG.
- Throws: Any error from the library, or a ``DNGManifestSlot/Failure``, for example if
  the signed store isn't the placeholder's size.

## `DNGManifestSlot`

internal, declared in `Sources/NopeSigning/DNGManifestSlot.swift`

```swift
enum DNGManifestSlot
```

Makes room for a Content Credentials store in a DNG while keeping IFD0 where it is.

Why this exists (issue #66): the C2PA library's own DNG writer appends a new copy of IFD0 at
the end of the file, with tag 52545 added, and points the header at it. ImageIO then no longer
recognizes the file as a DNG: measured on an iPhone 16 Pro Max with iOS 27.2.1,
`CGImageSourceCreateWithData` reports `public.tiff` with 0 images, and macOS 27 reports
`public.tiff` too. A DNG with the same tag inserted into IFD0 in place opens as
`com.adobe.raw-image` (`docs/TESTING.md`, "Signed DNG and ImageIO").

So the signer inserts the entry itself: tag 52545 (`0xCD41`), type UNDEFINED, in IFD0 at its
ascending tag position (C2PA 2.2, appendix A.3.3; TIFF 6.0, section 2: "The entries in an IFD
must be sorted in ascending order by Tag"), with the store at the end of the file. Every byte
after the new entry moves 12 bytes later, and every offset that points past it moves with it.
12 keeps every value on the word boundary TIFF requires. The C2PA library's data-hash
workflow then hashes the file with the store excluded and signs it, and the signed store
replaces the placeholder byte for byte (``ContentCredentialsSigner``).

Privacy rule: this adds the Content Credentials store and its entry and changes nothing else.
It never removes or rewrites a tag (AGENTS.md, "remove metadata through system APIs, never by
editing bytes"). It is byte-level code, so it is fuzz-tested (`DNGManifestSlotTests`), and the
signed file is read back against the allowlist like every other file.

Limits, each rejected with ``Failure``: classic TIFF only (not BigTIFF), at most
``maximumDirectories`` directories, a file that already has tag 52545, a value that crosses
the insertion point, and an offset stored as SHORT that would no longer fit. Data whose own
contents hold absolute file offsets can't be fixed up; of the tags nope. allows, only the
Apple maker note (`0x927C`) holds offsets, and those are relative to the maker note's own
start (an assumption from ExifTool's Apple maker note table, checked on a device with an
exiftool dump of a signed DNG: `docs/PRIVACY.md`, "Device checks").

## `InMemoryFile`

internal, declared in `Sources/NopeSigning/InMemoryFile.swift`

```swift
final class InMemoryFile
```

A growable byte buffer with a read and write position, for C2PA streams kept in memory.

Privacy rule: photos go from memory to Photos and never linger on disk (AGENTS.md, "Photos
never linger"), so the C2PA library reads the source file from, and writes the signed file
to, memory instead of temporary files. This type holds the logic, in safe Swift;
`InMemoryStream.swift` connects it to the library's pointer-based callbacks.

It behaves like a file opened for reading and writing: reading past the end returns no
bytes, writing past the end fills the gap with zeros, and seeking before the start fails.

## `SelfIssuedCertificate`

internal, declared in `Sources/NopeSigning/SelfIssuedCertificate.swift`

```swift
enum SelfIssuedCertificate
```

Builds the anonymous, self-issued X.509 certificate that carries one file's public key.

The certificate is signed by the file's own one-use key, so it isn't chained to any
certificate authority. Validators therefore show the signer as untrusted or unknown
(C2PA specification 2.2, §15.7, `signingCredential.untrusted`). That is expected and honest:
the signature proves the file hasn't changed since nope. signed it, not who took it
(docs/research/c2pa-signing.md, "Certificates and trust").

Privacy rule: every field except the key and the random serial number is the same for every
file and every person, so the certificate identifies no one and links no two files
(docs/PRIVACY.md, "Content Credentials"):
- the subject and issuer are only the common name ``commonName``;
- the validity is a fixed range, ``notValidBefore`` to ``notValidAfter``, so it doesn't
  reveal when the photo was taken;
- there is no email address, location, organization or device detail.

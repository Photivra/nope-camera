## `AVFoundationCaptureBackend`

public, declared in `Sources/NopeCapture/AVFoundationCaptureBackend.swift`

```swift
actor AVFoundationCaptureBackend
```

The real `CaptureBackend`: the device's cameras through AVFoundation.

It discovers physical cameras only, publishes their capabilities as plain values, and
captures single-frame Bayer RAW, or the labeled processed fallback on a lens without Bayer
RAW. Each photo's file is written with metadata built from the request's allowlist plan and
returned in memory; nothing is written to disk or saved here (`PhotoSaver` saves it).

The decisions live here and in ``LensCatalog`` and ``CapturePolicy``, all tested with fakes.
The calls that need a camera are in ``SystemCaptureHardware``, which is excluded from the
coverage gate and verified on a device (docs/TESTING.md).

Create it with ``init()`` in the app target.

## `AVFoundationCaptureBackend/captureBracket(_:frames:)`

public, declared in `Sources/NopeCapture/AVFoundationCaptureBackend.swift`

```swift
func captureBracket(_ request: CaptureRequest, frames: [BracketFrame]) async throws(CaptureError) -> [CapturedPhoto]
```

Takes a manual exposure bracket, in memory only, and rejects it if any frame is blank.

- Parameters:
  - request: The lens and format; must match the last ``startSession(_:)``.
  - frames: Each frame's ISO and exposure duration, from 1 to the lens's
    `maxBracketedPhotoCount`.
- Returns: One photo per frame, in order, each a separate single-frame photo.
- Throws: `CaptureError.notRunning` if the session isn't configured for this request,
  `CaptureError.captureFailed` for an invalid frame count or a missing photo,
  `CaptureError.blankPicture` if any frame is blank (all are dropped), or the hardware's
  error.

## `CaptureHardware/capture(_:metadata:)`

internal, declared in `Sources/NopeCapture/CaptureHardware.swift`

```swift
func capture(_ plan: PhotoSettingsPlan, metadata: MetadataPlan) async throws(CaptureError) -> HardwarePhoto
```

Takes one photo and writes its file with metadata built from the allowlist.

The file is flattened with `AVCapturePhoto.fileDataRepresentation(with:)` and a
customizer whose `replacementMetadata(for:)` returns
`MetadataPlan.properties(for:from:orientation:)` for the system's metadata: the header
says the returned dictionary replaces the photo's metadata (`AVCapturePhotoOutput.h`,
`AVCapturePhotoFileDataRepresentationCustomizer`). AVFoundation itself writes the RAW
image data, so the sensor data isn't re-encoded by nope. For a RAW photo the system's
own DNG is also flattened once, only to keep its RAW image data as a reference.

- Parameters:
  - plan: The photo settings to use.
  - metadata: The plan the file's metadata is built from.
- Returns: The file bytes, the reference RAW image data, a few bytes sampled from the
  photo's pixel buffer, and capture details.
- Throws: `CaptureError.notRunning` if the session isn't running, or
  `CaptureError.captureFailed` if the system reports an error or no file.

## `CaptureReadiness/waitUntilReady(timeout:interval:read:)`

internal, declared in `Sources/NopeCapture/CaptureReadiness.swift`

```swift
static func waitUntilReady(timeout: Double, interval: Double, read: @Sendable () async -> CaptureReadiness) async throws(CaptureError) -> Bool
```

Waits until the output reports ``ready``, so a capture isn't sent to an output that is
still preparing. Apple: "Capturing only when the output is ready limits the number of
requests inflight" (`AVCapturePhotoOutput.captureReadiness`).

The output still accepts requests when it isn't ready, so after `timeout` the wait ends
and the capture goes ahead.

- Parameters:
  - timeout: The longest wait, in seconds.
  - interval: The time between checks, in seconds.
  - read: Reads the current readiness.
- Returns: `true` if the output became ready, `false` after the timeout.
- Throws: `CaptureError.notRunning` as soon as the session isn't running.

## `PictureCheck`

internal, declared in `Sources/NopeCapture/PictureCheck.swift`

```swift
enum PictureCheck
```

Tells a blank photo buffer from a picture, cheaply, from a few sampled bytes.

On an iPhone 16 Pro Max (iOS 27.2.1) the camera service got stuck in a state where the
session ran, frames arrived and auto exposure metered normally, but every delivered buffer
was zero-filled: the RAW DNGs were a constant fill and the video frames' luma bytes were all
0, until the phone was restarted (docs/TESTING.md, "Black frames"). A sensor readout always
carries noise, so a real picture never has every sampled byte equal; a zero or constant fill
always does.

The hardware adapter reads the bytes at ``sampleOffsets(byteCount:)`` from the photo's pixel
buffer and ``AVFoundationCaptureBackend`` asks ``isBlank(_:)``. Reading 128 bytes costs
nothing next to a capture, so it runs on every photo.

## `PictureCheck/isBlank(_:)`

internal, declared in `Sources/NopeCapture/PictureCheck.swift`

```swift
static func isBlank(_ sample: [UInt8]?) -> Bool
```

Whether sampled bytes come from a blank (zero-filled or constant-filled) buffer.

- Parameter sample: The bytes read at ``sampleOffsets(byteCount:)``, or `nil` when the
  photo had no pixel buffer to read (a compressed HEIF or JPEG; Apple's
  `AVCapturePhoto.pixelBuffer` is `nil` for those).
- Returns: `true` only when there are at least ``minimumSampleCount`` bytes and they are
  all equal. `nil` or too few bytes give `false`: unknown is treated as a picture.

## `PictureCheck/minimumSampleCount`

internal, declared in `Sources/NopeCapture/PictureCheck.swift`

```swift

```

The fewest sampled bytes needed for a verdict; with fewer, the photo counts as a
picture, so a tiny or unreadable buffer never blocks the camera.

- Parameter byteCount: The size of the buffer, in bytes.

## `SystemCaptureHardware`

internal, declared in `Sources/NopeCapture/SystemCaptureHardware.swift`

```swift
final class SystemCaptureHardware
```

The AVFoundation implementation of ``CaptureHardware``: one `AVCaptureSession` with one
camera input and one photo output, configured on a private serial queue.

It owns the app's only capture session: lens switches replace the camera input inside one
configuration transaction on the same session, and ``stop()`` tears the session down in a
fixed order before anything else may configure it (docs/TESTING.md, "Black frames": after
the earlier Debug tag check built its own session per lens, the camera service delivered
blank frames to every app session until the phone was restarted).

Setup order: the `.photo` preset, camera input and photo output are committed first, so
the camera's active format is the photo format; then the output's processing switches and
an explicit `maxPhotoDimensions` from that format are committed before `startRunning()`, as
`AVCapturePhotoOutput.h` recommends for settings that reconfigure the pipeline; then the
photo settings are prepared (`setPreparedPhotoSettingsArray`), because RAW captures need
extra buffers; and each capture waits for `captureReadiness` to be `.ready`.

`@unchecked Sendable`: every mutable property and every session call is confined to
`queue`.

## `SystemCaptureHardware/stop()`

internal, declared in `Sources/NopeCapture/SystemCaptureHardware.swift`

```swift
func stop() async
```

Stops the session and tears it down, strictly in order, on `queue`.

1. `stopRunning()`, which "is synchronous and blocks until the receiver has completely
   stopped running" (`AVCaptureSession.h`), so nothing below overlaps a running session.
2. The camera input and the photo output are removed in one configuration transaction.

The method returns only after both steps, because the caller awaits `perform`. The next
``configure(_:)`` re-adds the input and output with the full setup order. This is the
only way a session is taken down: nope. never creates a second session, and never
starts one while another is still stopping (docs/TESTING.md, "Black frames").

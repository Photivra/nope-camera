### 2.1 What the 2026-11-21 decisions change

Numbers are the review's decision numbers. "Review decision 4" in this plan and in the design means number 4 below.

1. **The Lock Screen camera always writes to its session folder** and never to Photos, whatever its copy of the settings says. When the app is next opened with the iPhone unlocked, it files each capture by the setting at that moment, into Photos or the store. The destination no longer depends on the settings hand-off. Until a capture is filed the Lock Screen camera says "Kept…" (string 41), not "Saved." This changes the Photos destination too: a Lock Screen photo reaches Photos when the app is next opened unlocked, and the changelog and release notes say so. **Gate:** built only if R4 shows the session folder keeps its content through a restart, a week without the app being opened and low storage, and that its files, once written, cannot be read while the iPhone is locked. **If the gate fails,** the review's fallback (findings A1 and A2) is built, confirmed by the owner on 2026-11-21: nothing is kept in the session folder; a change of Save Photos To takes effect only once the app has read the Lock Screen camera's copy back, and a failed read-back is shown on the page as a change that was not made; with nope only in effect the Lock Screen camera does not take photos and says why (string 42); with Photos it saves as in 1.0.0.
2. **The backup question.** The first time nope only is chosen the app asks once, with neither answer preselected, whether captures kept in the app stay in this iPhone's backups. The answer sets Leave Out of Backups; the Save Photos To footer states the current answer. This replaces "Leave Out of Backups is off by default" (2026-11-18, decision 3) for anyone who chooses nope only.
3. **Leave Out of Backups keeps its name.** Its text says the app asks iOS, names only the backup kinds R4 confirmed, and says it does not cover other ways of copying the phone. The app sets the flag again after every write into the store, not only at launch, and a debug check reads it back.
4. **Re-lock delays are conditional.** Lock Again (1 minute, 5 minutes) is built only if R4 shows the app can tell that the iPhone was locked inside the delay. Otherwise 1.2.0 has Immediately only, with no Lock Again section.
5. **The library locks again inside the app:** when the library is closed, and when a capture's viewer opened from the camera is closed back to the camera.
6. **Nothing outside the lock.** With Lock Captures on, no thumbnail, preview or detail of a capture kept in the app is made or held outside the store's lock: no `SessionPhotos` record, and no preview in `pendingPhoto`, the saving state that #129 adds in 1.1.0. The Last Photo spot and that saving state show the neutral marker. This is the part of #129 that depends on #83; it is built here, not in 1.1.0.
7. **File names.** An exported name carries the date or time only when the Date and Time detail is in that file; otherwise it is random. Neutral File Names stays as an option that makes every name random. The rule is built with export (S2), so it holds if the option is cut.
8. **"Share Clean" is renamed** to a descriptive name, drafted as "Share Without Optional Details", and its summary carries the sensor-pattern sentence. This plan uses the new name; the issue's part 4, "Share clean", is the same work.
9. **The capture time stays in the store** for ordering and day sections when Date and Time is off. The Details in Each Photo footer says so (string 48), and `docs/PRIVACY.md` says so when S6 writes it. Apart from this, the manifest holds nothing the file's own detail switches removed.
10. **Factory Defaults** in the app leaves Save Photos To, Lock Captures and Leave Out of Backups unchanged, like the assistant route. This replaces "reset after authentication when Lock Captures is on".
11. **The cut rule.** The store does not ship without Lock Captures. If the lock is cut, parts 1, 2 and 5 move with it (and parts 4 and 6, which need them). This replaces the cut rule of decision 13. With #83 now the whole of 1.2.0, a cut of the lock means the release waits; the only parts that can be dropped on their own are Share Without Optional Details and then the Neutral File Names option.
12. **Share sheet actions removed:** Copy, Save Image, Assign to Contact and Print, plus any action a device check shows writes to Photos or a shared album. The app's own Save to Photos stays.
13. **The Lock Screen camera's Settings does not show** Save Photos To or Lock Captures. This replaces "read only".
14. **Two string reviews.** The owner reviews strings 20 to 24, 26 to 28, 30 to 33 and 36 from the design table before S1 starts, and every string again in the built app before the release run (decision 26, amended).

### 2.2 Rules added from the review's other findings

These need no owner decision. Each is a specification, test or device-check change; the finding is in brackets.

- **Three store states** (C1): available, unavailable (the iPhone's protected data cannot be read) and damaged. While unavailable the store reads, rebuilds, migrates, moves and deletes nothing, and a permission error is never treated as damage. A file that cannot be matched to the index is never deleted automatically. The file-system fake gains a "locked" mode used by every store, migration, delete and hand-off test, because the Simulator does not enforce Data Protection.
- **A capture is saved when its file and manifest are both written and read back** (G2). A file without a manifest is listed as a recoverable item. The low-storage warning counts the file, manifest and thumbnail.
- **Protection class** (C2, B5): files are created as class Complete when unlocked, as specified; a Complete write that fails at the moment of locking is retried once as CompleteUnlessOpen before the capture is reported as not saved. At each unlocked launch the store checks every file's class and raises any that is lower, including files moved from the session folder, whose class is set explicitly after the move (A2). If R4 shows Complete writes failing in a burst when the side button is pressed, capture files are created as CompleteUnlessOpen and raised by that pass instead.
- **The destination is fixed at the press** (G1) and travels with the capture through a burst, a series, a bracket and a pending save. Save Photos To cannot be changed while one is running.
- **Delete** (E1, E4): every delete also removes the session's records and previews of the deleted captures and resets the Last Photo spot. Delete All stops a running burst or series and discards pending saves first, then removes and recreates the store directory. The index is a file rewritten whole, so no entry of a deleted capture remains in it. The wording makes no claim about erasing storage.
- **The Lock Screen camera shows every failed write** (A3) with the existing "Not saved" state, and removes a partial file.
- **Authentication** (D4): the context never reuses an earlier device unlock (`touchIDAuthenticationAllowableReuseDuration` stays 0). Passcode Only gets its own explanation.
- **Export** (E7, D7): several captures are exported only after a free-space check; As Saved names a location when the file holds one.
- **The copy without optional details** (F6): the test asserts, per format, that every byte of the copy is image data, an allowlisted tag or required structure, so no embedded thumbnail, preview, XMP packet or leftover bytes remain.
- **The settings snapshot** (A1): a test fails the build when a full snapshot, every setting at its longest value, exceeds the hand-off's size limit. The destination no longer depends on the snapshot, but Shutter Sound, Half-Press (if 1.1.0 shipped it) and the Lock Captures state still reach the Lock Screen camera through it.
- **Wording** (B1, B3, B4, C3, C4, D5, D8, E6, F3, F4, F5, G3, H2): the rewritten strings in the design, section 9, and the limits list in the design, section 7, which S6 writes into the Honesty screen, `docs/PRIVACY.md` and the threat model in `docs/SECURITY_AUDIT.md` after the device checks.

### 2.3 Architecture and build groups

- A new adapter module, `NopeStorage`, beside `NopeCapture`, `NopeDevelop` and `NopeSigning`: the file system, Data Protection classes, the backup flag, LocalAuthentication and the Lock Screen session folder live there, each behind a protocol declared in `NopeCore` and tested with a fake. `NopeUI` still talks only to `NopeCore`. `scripts/check-architecture.sh` learns the module. It is not a new dependency.
- `NopeCore` gains the store's model and rules (`CaptureStore`, `StoredCapture`, the versioned manifest and the index that can be rebuilt from the files), the destination choice in `PhotoSaver` (the allowlist, read-back and signing run before either destination, unchanged), `CaptureLock` (the lock's state machine on `NopeClock`'s continuous clock), export and temporary-file cleanup, the export file-name rule, planning of the copy without optional details, and neutral file names.

S1 creates the gate's interface (`CaptureStore+Gate.swift`: whether the lock is on, whether the store is unlocked, and "content closed"), always open, and builds the library, the viewer, `SessionPhotos`, `PhotoSaver` and `pendingPhoto` against it. S3 supplies the real lock. So review decisions 5 and 6 need no second edit of S1's files.
- Thumbnails for the library are kept inside the store (decided, decision 16), with the capture time (review decision 9).

### 2.6 Risks and size

- **Risks:**
  - the size of the work (review decision 11 sets what is cut together before building starts);
  - losing someone's only copy: captures kept in the app are deleted with the app and are not in Photos. Upgrade fixtures, originals never rewritten, the three store states, the plain warnings, and the release gate of installing the previous build, taking captures and updating are all required before this ships;
  - captures leaving the phone in a backup without the person knowing (the backup question and the footer that states the answer);
  - Data Protection and the Lock Screen extension behaving differently from the documentation (R4, with a fallback named for each gate);
  - Lock Screen photos reaching Photos later than in 1.0.0 and 1.1.0 (stated in the Lock Screen camera's own sentence and first in the release notes);
  - the DNG rewrite: byte-level code in a privacy path (fuzzed, or not shipped; HEIF and JPEG only is the decided fallback);
  - a lock that guards screens but not data (enforced in the store; nothing held outside it; the route test);
  - wording that claims more than the checks show (the owner's first string review before S1, the Honesty review in the built app, and S6 writes the limits last).
- **Size:** XL: about five to seven weeks of building across the groups, plus the device checks. The review's changes add about a week, most of it in S1 and in tests.

- **The share sheet** (12): every action it offers for a DNG, a HEIF and a JPEG file, with the planned exclusions applied; which of them write to Photos or a shared album.
- **Two phones of one model** (13), if a second is available: the same scene and settings on both; every locked DNG tag and opcode list compared byte for byte.
- **Started while locked** (6): start the probe from the watch remote and from a Shortcuts automation with the iPhone locked; record the errors a read of a class Complete file returns, and that the file is intact after unlocking.
- **A write at the moment of locking** (7): a 20-file burst of class Complete writes with the side button pressed part-way; record which writes fail and how.
- **iPhone Mirroring** (8): an authentication prompt opened through a Mac, with the default policy and with passcode only; record what it accepts.
- **The app-switcher snapshot** (11) with the share sheet, the Files picker and a confirmation open, inspected in a downloaded container as `docs/SECURITY_AUDIT.md`, check 11, describes.
- **A clone as an export copy** (E7): whether a file-system clone of a class Complete file keeps its class. If not shown, exports are real copies.

## 4. Work order

### 4.1 Rules

- Groups in the same wave touch **disjoint files**, listed below. A group that finds it needs a file outside its list stops and says so.

- New UI tests go in the group's own new test file.
- Each group runs its own unit tests and its own UI test file locally before it is merged. The whole suite runs once on the integrated branch, when the machine is otherwise idle.
- A decision of section 7 that is still open blocks only the group that needs it.
- Briefs for any group that touches the camera screen repeat: Q is not changed.

By review decision 11: the cut order ends before Lock Captures; Share Without Optional Details is cut first, then the Neutral File Names option; the store does not ship without Lock Captures, and if the lock is cut, parts 1, 2 and 5 move with it. 14. **#83, the saved sentence with nope only.** *Decided 2026-11-21: (a).

## 3. Each issue

### 3.1 Apple Vision Pro (#114)

**Not in 1.1.0: a backlog item, in no release.** Kept as the research plan for when it is picked up.

**This is research with a decision at the end, not a promise.** Nothing about Apple Vision Pro appears in the app, the store page, the site or the changelog unless it is built and checked.

What the finding must answer, each from Apple's documentation for the current visionOS SDK and App Store rules, with the page cited:

1. What cameras does an App Store app get on visionOS: the main cameras, the front (Persona) camera, spatial capture? Through which API, with which entitlement, and is that entitlement open to App Store apps?
2. Can any of them deliver a single-frame Bayer RAW, or any still that is not a rendered Persona or a composited view?
3. What does the iPad app do today when run on Apple Vision Pro as a compatible app: which devices `AVCaptureDevice` reports, what the picture shows, whether RAW is offered, what the lens row and the HEIF fallback show? (visionOS Simulator, "Designed for iPad" destination; a look only, no test suite.)
4. For (a) the compatible iPad app and (b) a native visionOS target: what works, what does not, and what the App Store page would have to say.
5. Can the promises be kept as on iPhone: no network code, no analytics, the metadata allowlist and read-back, as little processing as the camera allows?
6. Can the project test it on hardware before claiming anything? (AGENTS.md: code that only runs on hardware is verified on a device before release.)

A first reading, **to confirm** (Apple developer forum answers and WWDC sessions on enterprise APIs for visionOS; nothing run): access to the main cameras is an enterprise entitlement for apps distributed inside an organization, not for App Store apps; a compatible iPad app that asks for the front camera gets the Persona, and has no useful rear camera; no RAW output is described. If that reading holds, a camera in this app's sense is not possible on Apple Vision Pro today, and the honest outcomes are to not offer the app there, or to offer it with a plain "no camera on this device" state that is of little use.

- **Deliverable:** `docs/research/vision-pro.md`: the answers with citations, the simulator observations with the Xcode and visionOS versions, the two options compared, and a recommendation.
- **Decision point:** the owner reads the finding and chooses go or no-go by the criteria of decision 21. A "go" gets its own design and build plan, and joins 1.1.0 only if it fits; a "no-go" closes #114 with the finding linked, to be looked at again with each major visionOS release.
- **One thing that cannot wait for the research:** a compatible iPad app is offered on Apple Vision Pro's App Store unless the developer turns that off for the app. Whether 1.0.0 is offered there before anyone has checked it is decision 20.
- **Risks:** documentation that is silent on RAW (then the simulator and, if available, hardware decide; with no hardware, no claim); a change in a later visionOS release (the finding is dated and re-read each release).
- **Tests:** none unless it is a "go".

With the setting off by default, 1.1.0 is silent for them until they turn it on. ### 3.4 CI: run only the jobs a change can affect (#85)

Diagram: `docs/design/release-1.1/ci-scope.svg`.

What exists: `build.yml` runs every job on every pull request and on pushes to `main`; `repo-checks.yml` runs the quick checks. `ui-tests`, `ui-tests-ipad`, `ui-tests-watch` and `oldest-os` are already small jobs that report the result of the jobs before them. There is no merge queue.

The design:

1. **A `scope` job** at the start of `build.yml`, on `ubuntu-latest`, with the whole history fetched. It runs `scripts/ci-scope.sh <base> <head>`, which lists the changed paths (`git diff --name-only -z --no-renames`, so a moved file counts at both its old and new path) and matches each against `scripts/ci-scope-rules.txt`, an ordered list of patterns and groups:

   | Group | Paths | Result |
   | --- | --- | --- |
   | app | `Sources/`, `App/`, `Tests/`, `Tools/`, `Vendor/`, `c2pa-lib/`, `Package.swift`, `Package.resolved`, `Config/`, `security/`, any `*.xcstrings`, `*.xcassets`, `*.docc`, `docs/api/` | full |
   | ci | `.github/`, `scripts/` | full |
   | docs | `docs/` (other than `docs/api/`), any `*.md`, `llms.txt`, `LICENSE`, `NOTICE` | light |
   | store | `store/` | light |
   | site | `site/` | light (the Pages workflow has its own checks) |
   | none | anything else | full |

   It prints `app=true` or `app=false` as the job's output, and writes the job summary: each changed path with its group (as data, in a code block, at most 200), and the reason for the result.
2. **Always a full run** when: the event is a push to `main`; the pull request is the release pull request (its head branch is named `release-*`, `release/*` or `int-*` and its base is `main`; decision 18); the pull request has the label `ci:full`; the base commit is missing, the diff is empty or the script fails.
3. **The heavy jobs** (`c2pa-lib`, the unit tests, `ui-build`, every shard, the watch jobs, the three oldest-OS jobs, `file-compat`, the DocC build) get `needs: scope` and run unless the scope said `app=false`. If the scope job itself fails or is cancelled they run.
4. **The required names keep reporting.** `ui-tests`, `ui-tests-ipad`, `ui-tests-watch` and `oldest-os` already are reporting jobs; their test becomes "the work passed, or the scope said it was not needed and the work was skipped". `unit-tests` and `docs` are heavy jobs today, so each is split: the work moves to `unit-tests-run` and `docs-run`, and `unit-tests` and `docs` become reporting jobs with the same rule. Each reporting job writes one line in its summary: "Ran and passed", or "Not needed for this change: only documents, store text or the site changed". A failed or cancelled work job always fails its reporting job. The names in the branch ruleset do not change (confirm the list against the ruleset before building).
5. **No workflow-level `paths` filter**, as the issue says: a skipped workflow leaves a required check waiting.
6. `repo-checks.yml` is unchanged and always runs whole; it gains the script's own test.
7. Path names from a pull request are untrusted input: they are read null-separated, never evaluated or used in a command line, and only `true` or `false` leaves the job as an output.

- **What it saves, plainly:** releases are built on one integration branch with one pull request and one CI run, and that run is always full. The saving is on pull requests that change only documents, designs, store text or the site, such as the one that will carry this plan.
- **Tests to add:** `scripts/test-ci-scope.sh` (run in `repo-checks`): documents only; app only; both; a path in no group; a CI file; a file moved from `docs/` to `Sources/`; a deleted file; an empty diff; a missing base; a string catalog under `docs/`; a path with spaces, a newline and shell characters; a documents path that contains the word `Sources`; more than 200 paths; the release-branch names; the label. A check that every job in `build.yml` either needs `scope` or is on a short list of jobs that always run, so a job added later cannot escape the rule unnoticed.
- **Documents:** `docs/TESTING.md`, "Continuous integration": which changes run which jobs, the full-run rules, and how to force a full run.
- **Risks:** a change that affects the app from a path classed as light (the rules list is short, fails toward a full run, and every release and every push to `main` runs everything); an expression mistake that lets a required name pass when its work failed (the reporting rule is one shared script with its own test, not five copies of an expression); renaming the two work jobs changes the names shown in the checks list (the required names stay).
- **Size:** S to M.

### 3.5 Quicker shooting with accurate save status (#129)

Design: [release-1.1.md](../design/release-1.1.md), section 3; figure `capture-status.svg`.

The rule that does not bend: **feedback at capture says a photo was taken; only a confirmed save says it was saved.** No change here alters a file or turns on a capture feature that changes what is recorded.

**Step 0: measure (research step R3).** On the test phone, for HEIF, RAW and RAW + HEIF, signing off and on, each rear lens and the front, 12 MP and the largest size, ten photos each: press to the camera starting the exposure; press to the camera returning the photo; press to saved (shutter ready again); and from a cold launch to the first live frame. `SaveTimings` already records the capture, develop, sign, read-back and save parts for Photo Details; R3 adds signposts for the two moments it lacks (exposure start, first frame), values marked private, no telemetry. The numbers go in `docs/TESTING.md` and decide step 3 and step 4.

**Step 1: feedback at the moment of capture.** A new `CaptureEvent` case for the exposure starting, sent by `AVFoundationCaptureBackend` from the capture delegate's "will capture" callback and by the simulated backend. `CameraReadyView` dims the picture for 0.1 s on it (rules for bursts, Reduce Motion and long exposures in the design, 3.2). The shutter haptic at the press exists; the sound is #128's.

**Step 2: the photo's own preview at once, shown as saving.** When the camera returns the photo, the Last Photo spot shows that photo's preview, dimmed, with a ring, not openable, labeled "Last photo, saving". On a confirmed save it becomes the normal thumbnail with today's seal, haptic and sentence. On a failure it is marked, the existing "Not saved: …" message shows, and then the last saved photo returns (decision 9).
- Model: a new `pendingPhoto` (preview and state) beside `captureStatus`, so `captureStatus` keeps its documented meaning for other interfaces built on `NopeCore`. `SessionPhotos` still holds saved photos only: nothing unsaved can be paged to in the viewer.
- The preview source is decision 12. R3 measures what asking the camera for a preview with a RAW capture costs (issue 104 found previews cost bursts something); if it slows the capture measurably, the spot shows the ring on a neutral tile instead.
- VoiceOver: "Photo taken. Saving." only when a save runs past 1 second (decision 11).

**Step 3: shoot again while earlier photos save.** Built only if the measurements call for it (decision 8). The shutter becomes ready as soon as the camera can take the next photo; saves run in order on a queue (new `SaveQueue.swift`), so Photos and the viewer keep capture order; the spot counts the photos still saving; the shutter is disabled again at the pending limit (decision 10), which is set by memory, not by a fixed number, because a pending RAW is tens of megabytes. Each photo gets its own result; a failure says how many of the pending photos were not saved. Leaving the app, the watch, Siri and the Live Activity keep their meaning: each reports its own photo after its save. This step changes the path that issues 100 and 101 fixed for 1.0.0, so it is built last, alone on those files, with those issues' tests kept as they are.

**Step 4: faster first frame.** Only where R3 shows time to save. Candidates to try and measure, none assumed to help: preparing the photo settings before the first press (`CapturePolicy` already builds the list for `setPreparedPhotoSettingsArray`), and the order of work at launch. Not candidates: responsive capture, zero shutter lag and deferred delivery, which stay off because they change which frame is recorded or how it is processed.

- **Settings and defaults:** none. Nothing here is a trade between speed and what the file contains, so there is nothing to put behind a switch.
- **Copy:** strings 8 to 12 of the design, all Honesty wording.
- **Code, steps 1 and 2 (group D):** `NopeCore`: `CaptureEvent.swift`, `CaptureBackend.swift`, `CapturedPhoto.swift`, `CameraModel.swift` (`capture`, `save`), `SimulatedCaptureBackend.swift`. `NopeCapture`: `AVFoundationCaptureBackend.swift`. `NopeUI`: `CaptureFeedback.swift` (`LastPhotoSpot`, `ThumbnailSlot`), `CameraReadyView.swift` (the picture's overlay, the `thumbnailOrShowControls` call, the announcement). ### 3.11 The Lock Screen camera never acts on an out-of-date settings copy (#134)

Design: [release-1.1.md](../design/release-1.1.md), section 9; figure `settings-copy-and-cover.svg`, panel A. Split from #83 (review finding A1).

A test fails the build when a full copy, every setting at its longest value, is over half the limit, so the state should not be reachable in a release.
  - **The Lock Screen camera with no copy at all** uses the first-launch settings, as today: every optional detail removed and signing off.
  - A change made in a Control Center control is handed over by the control as today; the app confirms it the next time it is in the foreground.
- **To confirm on a device (R8), before building:** that the app can read the app context back, and that what it reads is what the Lock Screen camera gets; how often the hand-off fails in practice; whether a control's hand-off arrives. **If the app cannot read the copy back,** only a thrown error and the size can be detected: the notice is built for those, string 114 is used for the rest, and the documents say the copy is sent, not confirmed.

### 3.35 Release: build and upload to TestFlight from CI (#160)

Figure: `docs/design/release-1.1/ci-release.svg`.

- **Decided (owner):** a manual workflow that archives and uploads to TestFlight with an App Store Connect API key the owner creates; manual dispatch only, never on pull requests.
- **The workflow, `.github/workflows/testflight.yml`:**
  - **Trigger:** `workflow_dispatch` only, with one input, the branch or tag to build. No `pull_request`, `pull_request_target`, `push` or schedule trigger. It is run from `main`; the input names the code to build.
  - **Job 1, `archive`: no secrets.** Checks out the input ref without stored credentials, builds the C2PA library as `build.yml` does, and archives `NopeApp` in Release with `NOPE_BUNDLE_IDENTIFIER=com.photivra.nope`, the build number from the run, and signing turned off. Runs the plist, launch-screen and App Store ID checks on the archive. Uploads the archive as an artifact and prints its SHA-256, the ref and the commit in the summary.
  - **Job 2, `upload`: environment `app-store`.** Waits for the approval the environment requires (decision 53). Checks out `main` only, never the input ref, so the only code that runs beside the key is the reviewed workflow and scripts. Downloads the archive, checks its SHA-256, writes the key to a file in the runner's temporary folder with owner-only permissions, signs and exports with cloud-managed signing, uploads to App Store Connect, and removes the key file in a step that always runs.
- **Secrets, for a public repository:**
  - The key ID, the issuer ID, the `.p8` key and the team ID are **environment secrets** of `app-store`, not repository secrets, so no other workflow or job can read them. The environment allows `main` only and has the maintainer as required reviewer.
  - Nothing in the repository holds a team ID, a key or a key ID. The export options are written at run time.
  - The job with the key uses only GitHub's own checkout and artifact actions, pinned to commit hashes, and no third-party action. No step echoes a secret or turns on command tracing; inputs reach scripts as environment variables, never spliced into a command line.
  - Workflow permissions are `contents: read`. Pull requests from forks never receive secrets, and this workflow has no trigger a pull request can reach.
  - `scripts/test-workflows.sh` (new, in `repo-checks`) fails if either release workflow gains a trigger other than `workflow_dispatch`, if a job that names `app-store` checks out anything but `main`, if an action is not pinned, or if a secret is named outside those jobs.
- **To confirm before building (R13):** that an archive made with signing off can be signed and exported with the API key, for the app, its extensions and the watch app; the least role the key needs. If an unsigned archive cannot be exported, job 1 also runs in the environment, and the environment's branch rule then limits builds to `main`, `int-*` and `release-*`.
- **Build numbers:** the run number plus a fixed offset above the last build uploaded by hand, recorded in `docs/RELEASING.md`.
- **Pre-release builds:** the same workflow with an integration branch as input gives an internal TestFlight build, in place of installing with `devicectl`. Debug builds for the research steps still need the Mac.
- **What stays the maintainer's:** creating the key and the environment (one time), approving each run, adding testers, and everything after the upload. The Xcode Organizer route stays in `docs/RELEASING.md` as the fallback.
- **Code (group Y, wave 0):** `.github/workflows/testflight.yml`; new `scripts/archive-app.sh`, `scripts/export-and-upload.sh`, `scripts/test-workflows.sh`; `.github/workflows/repo-checks.yml` (one step); `docs/RELEASING.md`.
- **Tests:** `scripts/test-workflows.sh` with passing and failing workflow files; the archive script against a fake `xcodebuild` (arguments, the build number, signing off); the upload script against a fake (the key file's permissions, its removal after a failure). The first real run is device check 26.
- **Risks:** a branch whose code misbehaves in job 1 (it has no secrets to take, and the maintainer sees the ref and commit before approving the upload); the key leaking through a log (no tracing, no echo, the file removed, GitHub's own masking as a second line); an Apple-side change to cloud signing (the Organizer route remains).

### 3.36 Release: the store text and screenshots from the repository (#161)

Figure: `docs/design/release-1.1/ci-release.svg`.

- **The workflow, `.github/workflows/store-page.yml`:** `workflow_dispatch` only, in the `app-store` environment, with the inputs mode (compare or publish), the version being prepared, and what to send (text, screenshots, or both).

### 3.37 CI: chosen UI tests on chosen devices, on demand (#162)

## 8. Decisions for the owner

Each has its options with the recommendation first, and one line of reason. Until a decision is made, only the group named waits.

1. **#120, the button's colors.** (a) **Recommended:** no fill, a ring and the eye in `#767676` (4.62:1 on black), full strength with Increase Contrast. (b) A dark fill `#1C1C1E` with the eye in `#8A8A8A` (6.08:1); the circle itself stays under 3:1, as today. (c) The dimmest that passes, `#5A5A5A` (about 3.0:1), with no margin. *Reason: (a) is the only one where both the eye and its circle pass 3:1 with room for measurement.* (Group B)
2. **#120, Night Mode.** (a) **Recommended:** drop the fill and dim the eye to the outline's red, `#CC0000` (3.57:1). (b) Drop the fill but keep the eye at full red (5.25:1). (c) Leave Night Mode as it is today. *Reason: pure red on black has little range, and (a) is the most that can be dimmed while passing 3:1.* (Group B)
3. **#128, people who update from 1.0.0.** (a) **Recommended:** off for everyone, as decided, with the change stated first in the release notes. (b) Off for new installs, on for people who update, so their phone sounds as it did. (c) Off for everyone, and a one-time note on the camera screen after the update. *Reason: one default is simpler to explain and to test, and matches the decision on the issue; the release note carries the change.* (Group C)
4. **#128, where the setting lives.** (a) **Recommended:** Settings › Camera, with a pointer row on the Accessibility page that opens it. (b) Settings › Camera only. (c) The Accessibility page only. *Reason: it is a camera behavior, and a person who relies on sound will look under Accessibility; one switch, two ways to reach it.* (Group C)
5. **#128, presets.** (a) **Recommended:** not stored in presets; Factory Defaults turns it off. (b) Stored in presets like other Camera settings. *Reason: applying a preset should never make a phone start, or stop, making noise.* (Group C)
6. **#128, a burst with the sound on** (after hearing it in R2). (a) **Recommended:** the system's sound for each photo, as the system plays it. (b) Silence during a burst even with the setting on, where the system allows, with the setting's text saying so. *Reason: the app cannot make one sound for a run, and (a) keeps "on" meaning one thing; choose (b) only if it is unpleasant in practice.* (Group C)
7. **#128, the rule in AGENTS.md.** "Hearing" says "The shutter sound follows the system." (a) **Recommended:** reword to "The shutter sound is the system's own. The app asks for silence unless the person turns Shutter Sound on, and never where the system requires the sound." (b) Approve other wording. (c) Leave the rule, and do not build the setting's off state. *Reason: the decided default cannot be built while the rule says the app leaves the sound alone.* (Group C)
8. **#129, how much to build in 1.1.0.** (a) **Recommended:** capture feedback and the early preview with its Saving state; shooting during a save only if R3 shows the median wait from press to shutter-ready is over 0.5 s for RAW on the main lens. (b) Build all three whatever the numbers say. (c) Measurements only in 1.1.0; the changes in 1.2.0. *Reason: the first two are low risk and visible; the third changes the shutter path fixed in 1.0.0 and should earn its place with numbers.* (Groups D, E)
9. **#129, a save that fails after the preview appeared.** (a) **Recommended:** the preview is marked "not saved" while the message shows and cannot be opened, then the last saved photo returns. (b) The preview is removed at once; the message alone reports it. (c) The marked preview stays until the next photo. *Reason: (a) shows which photo failed without leaving anything that looks like a kept photo.* (Group D)
10. **#129, how many photos may wait to be saved** (only if step 3 is built). (a) **Recommended:** a limit by memory, expected to be about three at 12 MP and one at the largest size, set from R3. (b) Always two. (c) One, as today. *Reason: a waiting RAW is tens of megabytes, and the largest sizes leave room for one.* (Group E)
11. **#129, VoiceOver at capture.** (a) **Recommended:** "Photo taken. Saving." only when the save takes more than 1 second; otherwise just the saved sentence, as today. (b) Always "Photo taken.", then the result. (c) Never; only the result. *Reason: one announcement for the usual photo, and no silence during a slow save.* (Group D)
